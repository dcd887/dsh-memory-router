> 测的是「模型会读到的 token」，不是端到端 LLM 成本。

## 2 这个 93% 不能直接引用

| 原因 | 说明 |
|---|---|
| 案例是挑的 | 这十个里有六个是刻意构造的「大文件」场景，专门用来验证节点会不会命中 |
| 真实负载里没有这么多大文件 | 实际一天几十次读取，多数是配置、源码、小 JSON |
| 命中率决定一切 | 命中时平均省 96%，未命中时省 0% |

按「三成读取能命中」折算：综合约 29%。这个数更接近真实，但仍是估计，不是实测。

## 3 值得单独看的三条

| 案例 | 为什么会省 | 省得对不对 |
|---|---|---|
| C1 税则大表 | 插件只返回「总条数 + 3 条样本 × 4 字段」 | 对：原读取只给了前 200 行，插件反而告诉了总条数 8972 |
| C2 盲推记录 | 只给标题骨架、错误行、结论行 + 文件元信息 | 对：这次只需要结论与卡点，不需要全表 |
| C6 超大 md | 只给 50 行标题 | 要打个问号：如果任务需要正文细节，这个替换会造成模型二次读取，那是净亏 |

C6 这条正好说明了 `reread` 科目的重要性：省 99% 看着漂亮，但如果模型因此又读一遍，实际是负收益。账本里记 `reread`，就是为了事后能算这笔。

## 4 口径与局限

| 项 | 说明 |
|---|---|
| 测量对象 | 工具返回内容替换前后的 token 差，用 `estimateByChars` 估（中文 1.5 字/token，ASCII 4 字/token） |
| 没测什么 | 端到端 LLM 调用成本（要真调模型、会有随机性、要花钱） |
| 没测什么 | 成功率变化（任务级 A/B 应该比「答对率」，这里没有判定器） |
| 可复现性 | 脚本自带 fixtures，落盘到临时目录，跑两次数字一致 |

## 5 下一步才能补的两块

| 缺 | 补法 |
|---|---|
| 真实命中率 | 连续跑几天，看账本里 `edg` 行数与总读取次数之比 |
| 成功率 | 固定 10 个有标准答案的任务，开/关各跑一遍，比答对率 |
